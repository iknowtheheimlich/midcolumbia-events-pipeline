# Resolver Pipeline

## Purpose

The Resolver Pipeline converts raw venue strings from source adapters into canonical Venue Registry records.

It exists so source adapters do not invent their own venue logic. That way lies chaos, duplicate venues, and eventually a spreadsheet named `final_FINAL_really_this_time.csv`.

## Input

The resolver receives normalized event objects that contain, at minimum:

- `venue`
- `city`
- `source`
- `url`
- `title`
- `start_date`

The resolver should preserve the original venue string even after a canonical match is found.

## Output

The resolver enriches the event object with venue metadata when a reliable match exists.

Potential enriched fields:

- `venue_id`
- `canonical_venue_name`
- `google_place_id`
- `resolved_address`
- `resolved_city`
- `venue_resolution_status`
- `venue_resolution_confidence`

New resolver fields should remain optional unless the schema is explicitly versioned.

## Resolution Flow

```text
Raw Venue String
      ↓
Normalize Venue String
      ↓
Check Google Place ID Index
      ↓
Check Venue ID Index
      ↓
Check Exact Canonical Name Index
      ↓
Check Alias Index
      ↓
Check High-Confidence Fuzzy Match
      ↓
Resolved Venue OR Unknown Venue Queue
```

## Match Priority

Resolution should follow this priority order:

1. Google Place ID match
2. Venue Registry ID match
3. Exact canonical name match
4. Known alias match
5. High-confidence fuzzy match
6. Unknown Venue Queue

Earlier matches should override later matches.

## Normalization

Resolver normalization may include:

- Trim whitespace
- Collapse repeated spaces
- Lowercase comparison key
- Remove punctuation for comparison key
- Normalize ampersands and `and`
- Normalize common suffixes
- Normalize city names

Normalization should be used for matching keys, not for destroying original source text.

## Confidence Rules

Automatic resolution should only occur when confidence is high.

Low-confidence matches should route to the Unknown Venue Queue.

When in doubt, quarantine. The queue is cheaper than bad registry pollution.

## Unknown Venue Queue

Unknown venue records should include:

- Original venue string
- Normalized venue key
- Source
- Source URL
- Event title
- Event date
- City if available
- Parser/adapter name
- Discovery timestamp if available

Unknown venues are reviewed later and either:

- Matched to an existing venue
- Added as a new registry venue
- Marked as non-venue/noise
- Deferred for more evidence

## Non-Venue Text

Some sources may emit non-venue values, such as:

- Online
- Various locations
- Multiple locations
- See event page
- TBD
- Private address

These should not become registry venues automatically.

They should either receive a known non-venue status or route to review.

## Registry Optimizer Dependency

The resolver should consume lookup tables generated by the Registry Optimizer rather than scanning the full Venue Registry during normal processing.

Expected lookup tables:

- Canonical name index
- Alias index
- Google Place ID index
- Normalized key index

The optimizer owns lookup generation. The resolver owns lookup use.

## Source Adapter Boundary

Source adapters must not resolve venues directly.

Adapters provide the best available raw venue value. The resolver determines canonical identity.

## Publisher Boundary

Publishers must not resolve venues.

Publishers consume already-resolved event objects and format output.

## Failure Behavior

Resolver failure should not corrupt publisher output.

Preferred failure behavior:

- Preserve original event.
- Mark venue as unresolved.
- Add item to Unknown Venue Queue.
- Continue processing if validation permits.

Hard failure should be reserved for malformed event objects or missing required schema fields.

## Test Expectations

Resolver tests should cover:

- Exact canonical matches
- Alias matches
- Google Place ID matches
- City disambiguation
- Known unknown venues
- Non-venue text
- Fuzzy match acceptance
- Fuzzy match rejection
- Queue output format
- Preservation of original venue string
